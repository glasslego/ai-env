## Jira Epic

- Epic 문서 작성·수정은 최신 epic-curator 표준 검증에 통과하도록 수행한다. 저장 후 구조·라벨별 필수 값·제목·파서 인식을 재검증하며, 공유 전 안내와 실제 오류를 구분한다. 상시 운영 Epic의 사용자 지정 예외는 유지한다.
- 관련 링크의 공유 글이 없으면 `* 아지트: 없음 (사유)`로 명시한다. `Agit: 미등록`처럼 인식되지 않는 표현이나 허구의 공유 링크는 쓰지 않는다.
- 템플릿을 먼저 확인한다. 일반 Epic은 배경 → 목적 → 기대효과 → 성공 기준 → 완료보고 → 관련 링크의 `☑️` 헤더·순서를 유지한다. 제목 태그나 다른 헤더로 임의 교체하지 않는다.
- 인바운드 describe의 8개 헤더, 원장 관리 마커, 공유 항목의 기존 헤더·본문 구조도 유지한다. 간소화한다고 모든 모드를 일반 Epic 6섹션으로 바꾸지 않는다.
- 배경·목적은 각각 1~2개 항목, 기대효과·성공 기준은 판단 가능한 핵심 항목부터 쓴다. 증거가 더 필요할 때만 늘린다.
- 실제 붙은 라벨의 rubric 필드를 빠짐없이 간결하게 채운다. `- [label] field: value`는 들여쓰기·기호·필드명까지 파서 형식을 유지한다. 상세 근거는 링크로 연결한다.
- allow_unknown=false 필드는 실제 근거로 채운다. 미정 허용 필드만 미정으로 쓰고 숫자·완료 상태를 만들지 않는다. 라벨 없는 분야의 rubric은 자동으로 추가하지 않는다.
- 완료보고: 완료한 결과·검증·남은 제약. 미완료 Epic은 아직 완료되지 않았음을 짧게 표시한다.
- 배경: 요청·합의가 담긴 Agit 또는 설계·정책 위키 링크를 근거로 붙이고, 핵심 문제만 1~2개 항목으로 요약한다.
- 코드·배치 Epic의 성공 기준과 완료보고는 세 가지 증거를 중심으로 작성한다.
  - GitHub: 관련 PR의 실제 머지 여부, 대상 브랜치, merged PR 링크. 브랜치가 존재하거나 push된 것만으로 머지 완료라고 쓰지 않는다.
  - 운영: 배치 변경은 cde-ranking-airflow의 prod 배포·반영 상태와 관련 DAG run/검증 근거를 남긴다. stage 성공이나 PR 머지만으로 prod 완료라고 쓰지 않는다.
  - 공유: 관련 결과·운영 안내를 작성한 Agit 글 링크를 남긴다. 요청 글과 결과 공유 글은 구분한다.
- 완료보고는 `코드 머지 / prod 반영 / Agit 공유`의 짧은 항목과 링크로 작성한다. 미완료 항목은 대기·미확인으로 표시한다. 코드·배치 배포와 무관한 Epic에는 해당하지 않는 완료 조건을 강요하지 않는다.
- 관련 링크는 배경 근거(요청 Agit·위키)와 결과 근거(merged PR·prod 검증·공유 Agit)를 구분한다. 긴 작업 이력을 반복하지 않는다.
- 담당자·상태·일정은 Jira 필드가 정본. 본문에서 반복하지 않는다. 단, roadmap:약속의 약속일정 등 rubric이 요구하는 필드는 생략하지 않는다.

- 개인 `epic-curator` 진입점을 먼저 사용한다. 선택한 모드의 팀 문서·CLI 도움말만 추가로 읽는다.

## 완료보고·주간 수집 호환

- 일반 Epic은 `☑️ 완료보고`, Task는 `h2. 완료보고`를 정확히 유지한다. `완료 근거` 등 다른 이름으로 바꾸지 않는다.
- 완료보고는 실제 결과·영향과 확인된 머지·운영 검증·공유 근거를 간결하게 적는다. `TBD`·`미정`만 남기거나 완료 결과를 댓글에만 쓰지 않는다.
- 헤더 인식과 주간 보고 포함은 별개다. 상태·resolution·상태전이·연결 이슈 반영일 등 선택한 수집 모드의 조건을 확인한다.

- Agit: 요청/결과 → 영향·확인 → 필요한 결정 → 근거 링크. 긴 회고·전체 작업 이력을 기본으로 붙이지 않는다.

- PR: 구체적인 문제와 변경 후 동작 → 검증 → 필요한 운영 사항. abandoned approach와 대화 이력은 생략한다.

## 위키 목차 형식 (2026-10-28)

- 제목은 번호를 붙인 계층으로 쓴다. Markdown 원본에서 `#` = `1. 개요`, `##` = `1.1. 소제목`, `###` = `1.1.1. 세부`.
- 첫 본문 섹션은 `# 1. 개요`다. 한두 줄 요약과 처음 읽는 사람이 필요한 정보만 둔다.
- 긴 상세·설계·운영 문서는 목차를 본문 맨 위, `# 1. 개요`보다 앞에 둔다. 개요 뒤에 목차를 일괄 배치하지 않는다.
  - Markdown 원본 첫 부분에 `<ac:structured-macro ac:name="toc" ac:schema-version="1" />` 한 줄을 쓴다.
  - cde-skills wiki 변환기가 이 매크로를 보존하므로 Storage를 따로 고치지 않는다.
- 짧은 안내·문서 모음·하위 페이지 목록 페이지에는 목차를 넣지 않는다. 섹션이 두 개 이상이어도 짧은 안내라면 목차를 생략한다.
- 사용자가 목차 위치나 기준 페이지를 명시하면 그 지시를 우선한다.
- 게시 후 Storage를 다시 읽어 긴 문서는 상단 목차 1개, 짧은 안내는 목차 없음, 제목 번호·계층이 유지됐는지 확인한다.
